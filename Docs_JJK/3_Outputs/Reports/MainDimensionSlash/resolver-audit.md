# Existing ActionResolver and Feedback Evidence

Inspected 2026-10-27. Research only; no runtime or asset edits. All values below describe the current dirty working tree, not approved replacement tuning. Paths and line numbers are repository-relative. This evidence supports the design phase and does not approve architecture.

User clarification during research: this is a NEW standalone action unlocked by a Potential. It does not replace Jailbreak Punisher or the existing cached Dimension Cut. Their details below establish constraints and reusable evidence only.

## Existing Potential unlock route

- `PotentialNodeDefinition` already has track, level, fragmentCost and unlockedByDefault (`Assets/Project/Scripts/Character/CharacterProgressionDefinition.cs:1120`); active nodes are selected by saved Potential level (`Assets/Project/Scripts/Combat/CharacterPassiveController.cs:1224`).
- `PotentialLevelActionCondition` supports a track and comparison against level (`Assets/Project/Scripts/Combat/ActionConditions.cs:104`). A new distinct StandaloneAction can use this existing condition to remain unavailable until the selected Potential level. Exact track and level are not yet selected.
- `PassiveActionModifierDefinition` also supports category+actionId/name, unlocked, priorityBonus and replacement keys (`CharacterProgressionDefinition.cs:405`). IMPORTANT: `IsActionUnlocked` starts true and only applies ACTIVE modifiers (`CharacterPassiveController.cs:657`); placing `unlocked:true` solely in the future Potential does not lock an action beforehand. Use the explicit level condition, or an intentionally authored base lock + unlocked Potential modifier. Do not assume missing modifier means locked.
- `ActionResolver.ResolveInitial` checks standalones before regular trees (`Assets/Project/Scripts/Combat/ActionResolver.cs:80`). `FindMatchingStandalone` filters triggerCategory/context, checks conditions/resources/unlock/availability and chooses RAW action priority (`:425`); its loop does not use the available GetEffectivePriority helper. Category or explicit input/context predicate must distinguish the new action from ordinary attacks and cached cuts; always-on matching would steal their input. Existing cached-cut priority is100.
- `StandaloneAction` derives directly from `CombatAction`; `Category` returns triggerCategory (`Assets/Project/Scripts/Character/ComboNode.cs:300`). It does NOT derive from SkillAction or UltimateAction. Selecting Ultimate trigger category alone does not grant the UltimateAction AE cost gate; selecting Skill category alone does not grant SkillAction cooldown behavior (`Assets/Project/Scripts/Systems/PlayerCharacter.cs:431–469`). More fundamentally, `PlayerStateMachine.CanStartSkillAction` requires `SkillAction` (`:705–723`) and `CanStartUltimateAction` requires `UltimateAction` (`:726–744`); the Skill/Ultimate state executors also check those subtypes. A plain StandaloneAction can match the resolver and still be rejected by those execution paths. Counter cost is already supported by resourceCounterId/resourceCost and committed once for a new counter action (`PlayerCharacter.cs:472`; `CombatPlayerState.cs:387`). Exact trigger/input, resource/cooldown policy, target requirements and precedence need human design choices before authoring.
- Give this action a unique stable ID distinct from `main.dash.dimension_cut` and `main.ultimate.jailbreak_punisher`. No new ID, Potential level, trigger category, cost or priority has been installed during research.

## Clock semantics and critical limitations

1. **Logic uses 60Hz and catches up discrete frames.** `FrameDataConstants.cs:9`; `FrameDataPlayerState.cs:217` advances in Update with unscaled delta only when explicitly requested; otherwise FixedUpdate uses fixed delta. The while loop at `:250` visits intervening logic frames. Hitbox offset0 is first active frame: `PlayerCombat.cs:1123` computes `frame - cachedStartupFrames - 1`. VFX/audio/action-event trigger frames are absolute step frames.
2. **Ordinary hitstop is GLOBAL.** `GameFreezeManager.cs:86` converts frames/60 to a real-time wait, sets Time.timeScale=0 (`:165`), then restores; enemy reactions also expose their own impact-freeze frames, but there is no demonstrated attacker-only global time channel. `HitBoxDamage.cs:280` requests hitstop once per hitbox activation, not once per target. Projectile-owned hitboxes skip the global freeze call (`:794`). Crits enforce at least 2 freeze frames (`:751`), even when a NormalHitbox authors zero; normal-vs-crit rhythm therefore needs testing.
3. **Do not run the damaging burst under AdvanceNodeUnscaledDuringFreeze unchanged.** CombatPlayerState permits its logic/events to advance (`:218`) and switches actor animator/motion to unscaled (`:567`), BUT `PlayerCombat.ProcessFrameFromState` returns immediately while HasActiveHitstop (`PlayerCombat.cs:302–307`). That skips normal hitbox, motion, audio and VFX processing. An event-only cinematic may advance while combat tracks do not. The design should prefer ordinary running action time for damaging bursts and brief holds between beats unless a later approved architecture addresses this gap.
4. **Freeze override is not implemented by the inspected event executor.** `freezeDurationOverride` exists in ActionEventEntry (`ActionEventFrameData.cs:101`) but has no read in CombatPlayerState. Overlay callback completes the sequence; authoring a shorter override does not currently shorten the hold.
5. **ScreenImpulse is scalar shake, not a directional camera path.** GameImpulseRequest has no vector, camera aim track, or lens curve. GameImpulseController emits real-time scalar pulses with a default output multiplier0.2 (`:107`, `:209`). Optional slow motion starts AFTER the pulse loop, then its own delay, not at event onset. Separate camera shove/recoil trajectory remains an unverified capability requiring later design/architecture review.
6. **Ultimate zoom is currently a smooth camera blend.** Despite the event tooltip saying instant zoom, CameraManager.SetUltimateZoom (`CameraManager.cs:1163`) raises the Ultimate camera priority and blends EaseInOut using `_ultimateTransitionDuration` (default0.35s at `:137`); fallback size lerp also uses unscaled time (`:1250`). It is not a per-frame attack lens track. Existing manager owns explore/combat/static/Ultimate cameras and room framing; external camera animation must not compete with it.
7. **Hit feedback may stack with authored feedback.** HitBoxDamage triggers background hit flash for EVERY ultimate-confirmed enemy hit (`HitBoxDamage.cs:291`). Hitstop/impact shake is once per activation if freeze>0 (`:280`, `:794`), while manually authored ScreenImpulse events are independent. Plan tests with crowds and crits to ensure automatic flash plus authored flash/impulse do not wash out the burst.
8. **Overlapping NormalHitbox windows are not independent simultaneous collider instances.** PlayerCombat iterates entries but drives a shared active hitbox and disables it on each entry's end (`PlayerCombat.cs:1123–1150`). Use non-overlapping timed windows for the first burst prototype; verify any overlapping/simultaneous damage shapes explicitly before promising them.
9. **Loop reset is selective.** Active wraps clear audio and hit state, reset hitbox activation and retrigger only VFX marked loopDuringActive (`PlayerCombat.cs:309–347`). Action-event deduplication is separately tracked in CombatPlayerState (`:461`), so action events are not naturally repeated every active-loop lap. Explicit burst entries are easier to audit than assuming all feedback loops identically.

## Cleanup and state boundaries

- CombatPlayerState.Exit commits output context, ends active sequence, stops afterimages, releases grabbed enemies, cancels/reset combat and resolver (`CombatPlayerState.cs:50`). Step changes also end active sequence and stop afterimages (`:392`). A freeze/overlay event should not straddle an auto-chain boundary unless its interruption is intentional.
- Sequence cleanup releases only its FreezeToken, stops overlay, releases player snap, restores zoom, UI fade and animator Normal mode, resets unscaled movement (`CombatPlayerState.cs:784`, `:814`). Pause holds are retained when restoring time (`GameFreezeManager.cs:258`).
- Pooled action VFX are tracked and stopped at step changes/cancel/reset (`PlayerCombat.cs:244`, `:683`, `:733`, `:1342`). Legacy prefab fallback returns null and is not tracked for step cleanup (`VFXSpawner.cs:71` onward); do not rely on it for clean interruption.
- Afterimage interval runs on scaled Time.deltaTime (`CombatPlayerState.cs:709`), so it stalls during a world freeze even when actor animation is configured unscaled.
- ScreenImpulse coroutines are launched on the persistent GameImpulseController and expose no per-action cancellation handle (`GameImpulseController.cs:209`). Their tails can continue after action interruption. AudioEntry.duration is visualization metadata (`AudioFrameData.cs:35`), not demonstrated sound cancellation or envelope control.

## Design-stage conclusions

The existing system can author a finite sequence of distinct slash visuals, non-overlapping damage windows, audio accents, brief holds, background flashes, and a final giant VFX while keeping the actor separate. It does not yet demonstrate frame-authored directional camera motion, independent actor/target freeze with all action tracks live, or a working freeze-duration override. These are evidence gaps to design around or explicitly review after the human design checkpoint. No new framework or dependency is justified during this research phase.

Prioritize a rhythm-only prototype with placeholder art after approval: test single enemy, crowd, critical hits, whiff, interruption, room boundary, pause, 30/60/120fps, and repeated casts. Verify every intended damage/VFX/audio beat fires once and returns camera/time/motion/UI to the correct owner.

## Independent review of proposed starting timeline

This is a feasibility review of proposed STARTING VALUES, not architecture or feel approval: brace0–11; burst contacts12,20,27,33,38,42; compression44–53; final54; recovery60–65; control/cancel66; VFX tail83. First/last burst request2-frame confirmed-hit stop, final6; no continuous world freeze/slow motion through burst.

- **Frame mapping:** startupFrames11 gives first active12. Hit offsets are0,8,15,21,26,30,42. If active continues through59, activeFrames48 and recovery starts60. Set total>=66 for cancelWindowStartFrame66 to be reachable; ending TotalFrames65 makes66 Done, not Cancel. Contact windows must end before subsequent windows and before Recovery; a two-frame contact12 window would end at14 (active12,13). Non-overlap is compatible with current shared hitbox.
- **Wall-clock rhythm:** these are ACTION frames. The requested freezes add up to10 real-time frames when all relevant contacts hit; they add0 on whiff. Middle critical hits enforce2 frames even with authored0, adding up to8 further real-time frames for four middle crits. Do not describe the sequence as fixed1.1-second real duration. Crowds, criticals and whiffs must be recorded separately.
- **Interrupt promise:** a Normal-category standalone runs PlayerAttackState's BasicAttack/AirborneAttack interrupt policy. Active accepts Skill/Ultimate/Jump/Dash, and Recovery permits movement/other actions (`Assets/Project/Scripts/Player/InterruptPolicy.cs:165`; `PlayerAttackState.cs:29`). Therefore the current system does not promise full commitment until66 or no movement before66 merely from step frame authoring. Decide desired interrupt behavior at the design checkpoint; policy changes need later architecture review.
- **Tail promise:** tracked step VFX die on reset, accepted cancel, next step, or natural action completion. Returning to locomotion at66 while guaranteeing tail through83 is not demonstrated by the existing stepVFX lifetime. Either accept intentional tail truncation with control, keep the authored action alive longer with a reviewed input policy, or review independent tail ownership later. A legacy prefab avoids tracking but has weaker cancellation cleanup and is not a solved design answer.
- **Camera/room bounds:** normal combat zoom is limited against room bounds (`CameraManager.cs:358`), and temporary player snap explicitly refuses static room reframing (`:819`). Ultimate camera has separate priority/size behavior. Validate tight rooms, room edges, static rooms and extreme aspect ratios before promising a camera push or large giant-cut composition. Do not copy current Attack2's +9X motion into the new stationary burst without an explicit motion decision.

## Existing contextual input conditions

`Assets/Project/Scripts/Combat/ActionConditions.cs` supplies:

- DirectionActionCondition `direction` (`:55`): Neutral/Forward/Back/Up/Down/Any from the directional vector; vertical takes priority (`InputContext.cs:34`). It is a direction hold, not an arbitrary button/chord.
- PreviousStateActionCondition `previousState` (`:67`): exact FSM state enum such as Skill; not prior actionId or completed-action history.
- RuntimeTagActionCondition `tagType`, `tag`, `shouldExist`, `applyOnActionStart` (`:128`): use an explicit Custom tag for standalone selection. The StepName variant needs a supplied StateContext.stepName and is not a historical skill identity.
- PotentialLevelActionCondition, RuntimeCounterActionCondition, RuntimeEffectStackActionCondition and ground/air/wall/grab predicates. No inspected action condition exposes combo depth or arbitrary held attack/skill button. `StateContext` adds current activeFrame and stepName, not action history.

**Skill then Attack:** direct Skill Recovery -> Attack transition is already possible (`PlayerStateMachine.cs:429`; Skill interrupt policy allows BasicAttack in Recovery). PreviousStateActionCondition=Skill can constrain actual Attack-state resolver selection because FSM stamps previous state on transition (`PlayerStateMachine.cs:168`; `CombatPlayerState.cs:306`). However the preflight `PlayerCharacter.BuildActionInputContext` does not populate previousState (`PlayerCharacter.cs:522`), and the subsequent live resolver does; test the whole path rather than testing the condition alone. Existing ordinary Normal actions provide a fallback, but condition-only availability previews can disagree.

This direct previous-state condition does not enforce a particular Skill ID, successful completion, a time window, or single use. `transitionContext.previousState` remains Skill during the entered Attack state, so a reselecting action can remain eligible until its state changes.

**Existing data candidate for a precise action identity:** a Potential's `PassiveRuntimeTagEffectDefinition` can filter the exact source skill actionId, add a timed custom tag at OnActionStarted/OnActionEnded/OnHitDealt, and remove that tag at the new standalone's OnActionStarted. The new Normal-trigger standalone requires PotentialLevel + that Custom runtime tag. Definitions: `CharacterProgressionDefinition.cs:72`, `:119`, `:542`; application: `CharacterPassiveController.cs:2687`. It supports a one-use contextual input concept without introducing a new button, but the desired opening event and duration remain human design choices. OnActionEnded is emitted by ResetCombo and CancelCurrentAttackButKeepComboProgress (`PlayerCombat.cs:681`, `:731`), so it includes cancellation, not just successful natural completion. A successful-Skill-only/completed-Skill-only promise must be validated explicitly before selecting this route.
